# hela-needle-tuning

Data, evaluation, training and release gating for the Needle models the HeLa runtime uses to pick tools (the native agent `hela.agent.run` and the Mitosis planners). This repo is public. It holds the code, the hand-written seeds, a snapshot of the public tool catalog and, once a model passes the gate, the **finished per-profile models** as release assets with checksums in [`models/manifest.json`](models/manifest.json). It contains no real session data. Training runs stage their output in a private repo; a model reaches the public release only through `scripts/publish_models.sh`, after passing the gate. Needle 3 is Apache-2.0, so fine-tuned versions may be redistributed with the licence and [`NOTICE`](NOTICE).

The runtime stays unaware of this repo. It loads whatever `NEEDLE_ENGINE_PATH` / `NEEDLE_MODEL_PATH` / `NEEDLE_SYSTEM_PATH` point at, so shipping tuned weights is a configuration change, not a code change.

## Use a finished model

Once published, each profile has a ready-to-use model: find it in [`models/manifest.json`](models/manifest.json) (URL, sha256, scores), verify the checksum, and point `NEEDLE_MODEL_PATH` at it. If anything is missing or fails, keep the shipped `needle3.cact`. Details in [`models/README.md`](models/README.md). **No model is published yet**: the first tuned model did not pass the gate, and nothing is released until it does.

## Train your own Needle (one line)

Each HeLa profile (`dev-workspace`, `minimal`, `research`, ...) can get its own small Needle model tuned on that profile's tools. Every canonical profile includes the Mitosis cell, and the installer enables Needle for any profile with Mitosis, so all 8 profiles use one.

**You need** an NVIDIA GPU machine (a rented 24 GB card is plenty; see `docs/TRAINING.md`), and either a *private* GitHub repo for the results plus a fine-grained token limited to that repo (Contents: write, 1-day expiry), or `NO_UPLOAD=1` to just keep the files. Never use a broad token on a rented machine.

```bash
export GH_TOKEN=<fine-grained token for your PRIVATE results repo>; curl -fsSL https://raw.githubusercontent.com/Hela-Ecosystem/hela-needle-tuning/main/scripts/runpod_train.sh -o t.sh && RUNS_REPO=<you>/<private-repo> PROFILES=dev-workspace bash t.sh
```

Without GitHub: `curl -fsSL https://raw.githubusercontent.com/Hela-Ecosystem/hela-needle-tuning/main/scripts/runpod_train.sh -o t.sh && NO_UPLOAD=1 PROFILES=dev-workspace bash t.sh`, then copy the printed run folder off the machine before you terminate it.

`PROFILES` takes one or more profile ids (`PROFILES="dev-workspace minimal"`) or `ALL` for all 8. The script builds each profile's dataset, fine-tunes with the Cactus CLI, exports `hela-needle3-<profile>.cact`, and records timings, coverage and logs. It never terminates the machine for you: do that when it says so.

**Then check the model before using it.** On a machine with the Needle engine, `ENGINE=<needle3> BASE_MODEL=<shipped needle3.cact> scripts/eval_profiles.sh <folder with the .cact files>` scores each profile's model against the untuned one on a frozen, hand-written eval and applies the release gate. A model that does not pass the gate should not be used. Needle's answers change with the system text the runtime passes (we measured 16 of 40 answers differing with and without it), while training rows carry none, so also run it with `SYSTEM_MODE=none` and give the installer whichever setting scores better.

Status: the single-profile path ran end to end once (see `docs/TRAINING.md`); the multi-profile loop and `eval_profiles.sh` are new and untested on a GPU. Needle 3's repository ships the Apache License 2.0 (`LICENSE` file and `license: apache-2.0` in its model card), which permits modified redistribution with the licence and notice kept; check the details yourself before sharing a model.

## Why

The untuned `needle3` is a general single-shot function caller. Against the HeLa catalog it makes selection mistakes, for example choosing `list_directory` for "what time is it in Jakarta". Fine-tuning on the catalog's own tools and prompts is the fix. Cactus reports large gains from this kind of tuning; we measure ours against a frozen eval instead of trusting that.

## Layout

| Path | Purpose |
|------|---------|
| `data/catalog/` | Snapshot of the bundled tool catalog and system prompt (from the public chaining-mcp assets, 2026-10-23), so the repo builds with no other checkout. Refresh it when the catalog changes. |
| `data/seed/*.jsonl` | `core.jsonl` is hand-written; `expanded.jsonl` is generated by `scripts/expand_seeds.py`. Fields: Each line: `task`, `tool` (qualified name, `done`, or `null`), optional `arguments`, `shortlist` (pin exact candidates), `regression`, `note`. |
| `src/hela_needle/` | Catalog loader, row builder, scrubber, split, eval runner, gate, CLI. Standard library only. |
| `eval/baselines/<profile>.json` | Scores of the shipped, untuned `needle3` on each profile's frozen eval (profile system text passed). The gate compares each profile's model against its own baseline. `eval/frozen.sha256` pins the eval. |
| `scripts/runpod_train.sh` | Runbook for a rented GPU pod: build data, fine-tune, export, record cost. Written, not yet run. |
| `docs/PLAN.md` | Milestones, acceptance criteria, risks, open questions. |
| `docs/TRAINING.md` | The training and export procedure, and what is still unverified. |
| `tests/` | Unit tests (`python -m unittest discover -s tests`). |

## How rows mirror the runtime

`hela-runtime/src/agent.ts` calls Needle in two stages, and the builder reproduces both prompts exactly, so the model is tuned on the text it will see:

1. **choose**: up to 4 candidate tools with empty parameter schemas plus a `done` tool. Answer: a tool name.
2. **arguments**: the one chosen tool with its full schema. Answer: the arguments.

If the runtime prompts change, update `examples.py` in the same change, or the tuned model drifts from what runs in production.

## Usage

```bash
export PYTHONPATH=src
A=/path/to/chaining-mcp/assets/needle   # engine and weights (catalog and system prompt are in data/catalog)

# build train/eval files (fails on an unknown tool or invalid arguments)
python -m hela_needle build-data --catalog data/catalog/hela-stack-tools.json

# nothing secret may reach a data file
python -m hela_needle check-secrets data/build/train.jsonl data/build/eval.jsonl

# score weights, then gate them against the baseline
python -m hela_needle eval --engine $A/needle3 --model $A/needle3.cact \
  --system data/catalog/hela-system.txt --out eval/candidate.json
python -m hela_needle gate --candidate eval/candidate.json
```

The catalog file is the bundled asset (292 entries, all 10 organelles). Rows are drawn per profile (`data/catalog/profiles.json`: which cells each runtime profile activates), so the candidate tools match what the runtime would shortlist. `python -m hela_needle coverage --catalog data/catalog/hela-stack-tools.json` regenerates `docs/COVERAGE.md`, the tracker of what the data teaches per tool, cell and profile. Prefer a fresh export of the live catalog when cells change.

## Rules

- **The split is frozen by hash of the task text**, so adding rows never moves an existing one between train and eval. Regression rows are always eval.
- **Regression rows are real mistakes** and must pass 100% before any release. Add one for every new selection failure seen in production.
- **Scrub before committing data.** `check-secrets` must be clean. Weights never go into git: they ship as release assets, with checksums in `models/manifest.json`. Checkpoints and built data are ignored by `.gitignore`.
- **The gate**: eval set of at least 20 rows, `choose_tool_acc` at least 0.02 above baseline, no drop in `args_valid`, regression rows all passing.
